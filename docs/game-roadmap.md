# «Печать сумрака»: дальнейшая разработка

Дата: 2026-10-16. Комнаты и сетевая тренировочная арена (шаги 1–2) реализованы: код приглашения, готовность, запуск, движение, столкновения и Shift. Инструкция: [комнаты и арена](rooms-and-arena.md). Следующий этап — короткий бой. Последующие шаги остаются дорожной картой, а не обещанием уже готовых возможностей.

Предложение следующего этапа: [первый совместный бой](next-combat.md). Ручная проверка двух полных клиентов пользователем пока отложена; её нужно выполнить перед внешним показом.

## Отправная точка и цель

Сервер аккаунтов, PostgreSQL, Gradle и клиент libGDX уже реализованы. Пользователь подтвердил, что клиентский этап полностью работает. Сохраняем существующие аккаунты, авторизацию и миграции.

Зафиксированные ранее требования:

- Кооперативное фэнтезийное выживание на одной арене для 2–4 игроков.
- Успешный забег занимает примерно 30 минут; поражение может наступить раньше.
- WASD — движение, мышь — прицеливание, левая кнопка — атака, Shift — рывок.
- Один стартовый герой — маг, три обычных типа врагов, один босс, 6–8 улучшений.
- Опыт и уровень команды в забеге общие; улучшения каждый выбирает себе.
- Уровень и сборка сбрасываются после забега, опыт аккаунта сохраняется отдельно.
- Java 21, Spring Boot, libGDX, Gradle и PostgreSQL остаются основой проекта.

Предлагаемые ниже тайминги, правила комнат и переподключения — новые проектные решения. Их можно уточнить до реализации соответствующего этапа.

## Порядок работы

Рекомендуемый путь — сначала проверить совместную игру на маленьком законченном примере, затем наращивать контент. Сначала полностью одиночная игра отложила бы проверку самой важной для проекта части — сети. Разработка сразу полного получасового забега связала бы слишком много непроверенных систем.

| Шаг | Что добавляем | Проверяемый результат |
| --- | --- | --- |
| 1. Комнаты | Создание, код приглашения, состав, готовность и старт; WebSocket для обновлений | Два клиента под разными аккаунтами видят одну комнату; пятый участник не принимается |
| 2. Сетевая арена | `game-core`, один уровень, персонажи, движение, столкновения и Shift | 2–4 игрока одновременно двигаются в одном мире; сервер определяет итоговые координаты |
| 3. Короткий бой | Один враг, снаряд мага, здоровье, смерть, победа и поражение | Можно пройти законченный тестовый бой на 3–5 минут и вернуться в комнату |
| 4. Игра через интернет | Размещение тестового сервера, HTTPS/WSS, переподключение, проверка задержки | Друг подключается со своего компьютера из другой сети и участвует в коротком бою |
| 5. Прокачка | Общий опыт команды, личный выбор улучшений, 6–8 вариантов | Два мага получают общий уровень, но собирают разные усиления; выбор не останавливает команду |
| 6. Результаты | История матчей и участников, начисление опыта аккаунту | Результат сохраняется после повторного входа; повторная обработка не выдаёт награду второй раз |
| 7. Полный забег | Три типа врагов, волны, передышки и финальный босс | Полный цикл примерно на 30 минут с понятной победой или поражением |
| 8. Завершение MVP | Графика и звук, читаемость боя, нагрузка, упаковка и документация | Игру можно отдать друзьям и показать в портфолио с воспроизводимым запуском |

Графику подключаем постепенно со второго шага. Последний шаг улучшает уже работающую игру.

## Архитектура игры

Один Spring Boot процесс обслуживает аккаунты, комнаты и игровые сессии. Отдельный игровой сервер как второй сервис сейчас не нужен. На нём могут существовать несколько независимых комнат; ошибки или команды одной комнаты не должны менять другую.

| Модуль | Дальнейшая ответственность |
| --- | --- |
| `client` | Экраны, ввод, камера, анимации, эффекты, звук и сетевое подключение |
| `protocol` | Сообщения комнат, команды управления, снимки мира и события матча |
| `game-core` — новый | Движение, столкновения, здоровье, снаряды, враги, опыт и правила победы; обычная Java без Spring, libGDX и БД |
| `server` | Авторизация, комнаты, запуск расчёта `game-core`, рассылка состояния и запись результатов |

Клиент отправляет намерение: направление движения, направление прицеливания, нажатие атаки и рывка. Он не сообщает серверу, какой урон нанёс, сколько получил опыта или куда телепортировался. Эти решения принимает сервер.

Начальные рабочие параметры: расчёт мира 20 раз в секунду, рассылка снимков 10 раз в секунду, отрисовка около 60 кадров в секунду. Это стартовые значения для измерений, а не обещание производительности. Клиент сглаживает движение других игроков между снимками; предсказание собственного движения добавляется на этапе движения, если измеренная задержка этого требует.

Сетевые обработчики кладут команды в ограниченную очередь; состояние комнаты и мира меняется последовательно. Движение хранится как последнее актуальное состояние ввода, а не как бесконечный список нажатий. Сервер обнуляет устаревший ввод, чтобы персонаж не продолжал идти после потери соединения. Медленный клиент не должен задерживать игровой расчёт и остальных участников.

HTTP остаётся для аккаунтов и операций комнаты. Постоянное соединение WebSocket доставляет события комнаты и затем игровые сообщения. Используем обычные сообщения JSON, без STOMP и брокера на первом игровом этапе. Ограничения размера и частоты сообщений, версия протокола, номера команд и снимков закладываются сразу.

Клиент Java может передать существующий Bearer в заголовке WebSocket handshake. Сервер берёт личность из проверенной сессии; токен в URL и новая система JWT не нужны. Истечение или отзыв сессии должны завершать доступ и через уже открытое соединение.

При добавлении новых экранов выделим экран комнаты и экран матча из текущего приложения. Рабочая логика регистрации и входа сохраняется; общими ресурсами интерфейса продолжает владеть приложение.

## Ближайший этап: комнаты

В меню появляются «Создать комнату» и «Присоединиться по коду». Экран комнаты показывает название, код приглашения, имена участников, владельца и готовность каждого.

Предлагаемые правила:

- Максимум четыре участника; для обычного старта нужно минимум двое и готовность всех.
- Запуск нажимает владелец. Проверка условий и переход к старту выполняются атомарно на сервере.
- Один аккаунт одновременно участвует только в одной комнате или матче.
- В уже начавшийся матч новые участники не входят; вернуться может его прежний участник.
- После выхода владельца из ожидающей комнаты права переходят оставшемуся участнику. В начавшемся матче владелец не обладает особыми игровыми полномочиями.
- Комната существует в памяти; пустые комнаты удаляются. Перезапуск сервера не восстанавливает открытое лобби.
- Любое изменение состава или готовности приходит остальным участникам автоматически. У снимка комнаты есть номер версии, чтобы запоздавший ответ HTTP не затёр более новое состояние.

Этот этап готов, когда несколько реальных окон клиента синхронно показывают состав и готовность, сервер корректно отклоняет лишнего участника и повторный старт, а соседние комнаты работают независимо. Переход к экрану ожидания матча можно проверить до появления игрового мира; незавершённая арена не объявляется готовой.

## Арена, бой и совместное выживание

Первый уровень — фиксированная арена с небольшим числом препятствий и общей картой столкновений для сервера и клиента. Маг выпускает снаряд в сторону мыши при удержании левой кнопки; частоту атак проверяет сервер. Рывок имеет ограниченную дальность и время восстановления и не проходит сквозь стены. Неуязвимость во время рывка — отдельное правило баланса для этапа боя.

Сначала реализуется один преследующий враг. Затем добавляются более быстрый слабый враг и медленный прочный. Препятствия и выбор пути должны проверяться вместе: враг не должен бесконечно идти в стену. Ограничение количества живых врагов и снарядов задаётся до нагрузочных проверок.

Для совместной игры предлагается возможность поднять павшего союзника, оставаясь рядом и удерживая E. Длительность, окно спасения и возвращение выбывшего игрока определим в дизайне боя, чтобы не оставлять друга зрителем на большую часть получасового забега. Если вся команда одновременно выведена из боя, матч завершается поражением.

Первый бой длится 3–5 минут и использует те же правила времени и завершения, которые позднее обслужат длинный забег. Продолжительность берётся из серверной конфигурации, а не из отдельной демонстрационной реализации.

## Прокачка и длительность

Убийства заполняют общую шкалу опыта. При повышении уровня каждый участник получает свой выбор из доступных усилений. Начальный набор: урон, скорость атаки, максимальное здоровье, скорость движения, сокращение восстановления рывка, дополнительный снаряд и один-два эффекта вроде пробивания или замедления.

Выбор делает сервер: клиент получает предложение и отправляет выбранный идентификатор. Сервер проверяет, что вариант действительно предложен и ещё не выбран. У каждого улучшения есть предел ранга.

Предлагается 10 секунд на выбор без общей паузы. При истечении времени сервер выбирает первый предложенный вариант; это правило видно в интерфейсе. Все такие окна входят в обычное время матча. Во время выбора управление персонажем должно оставаться доступным.

Рабочее расписание полного забега:

| Время от старта | Содержание |
| --- | --- |
| 0–5 минут | Простые враги, первые уровни и знакомство с ареной |
| 5–12 минут | Второй тип врага и более плотные волны |
| 12–20 минут | Все три типа и сочетания угроз |
| 20–27 минут | Усиленные волны и проверка собранных улучшений |
| 27–28 минут | Короткая передышка и предупреждение о боссе |
| 28–30 минут | Финальный бой |

Таймер ведёт сервер по прошедшему времени, а не просто по числу выполненных тиков. Босс убит — победа; вся команда выведена из боя или 30 минут закончились при живом боссе — поражение. Успех обычно приходится на 28–30 минут. Первые значения будут корректироваться по прохождениям с друзьями.

## Данные и сохранение

Текущие `accounts`, `player_profiles` и `auth_sessions` остаются. На этапе результатов новая миграция Flyway добавит `matches` и `match_players`; `V1` не редактируется, БД не пересоздаётся.

- `matches`: идентификатор, статус, начало и завершение, длительность, версия конфигурации.
- `match_players`: матч и аккаунт, нанесённый урон, убийства, достигнутый уровень, итоговые улучшения и начисленный опыт аккаунта. Пара `(match_id, account_id)` уникальна.
- `player_profiles.account_xp`: постоянный опыт, начисляемый только сервером. Он отделён от уровня и усилений конкретного забега.

Матч и состав фиксируются при старте. Завершение матча, статистика и награды записываются одной транзакцией. Одной уникальности участия недостаточно: начисление также защищается однократным переходом матча из активного состояния в завершённое, чтобы повторный запрос не удвоил опыт.

Координаты, здоровье и снаряды живут в памяти, без SQL на каждом игровом шаге. При временной ошибке сохранения итог ожидает повторной записи, а игровой цикл других комнат продолжает работать. Полное восстановление матча после аварии сервера не входит в первый MVP: оставшиеся активными записи помечаются прерванными, незавершённые награды не выдаются как якобы сохранённые.

В меню появляется история своих матчей. Начальный постоянный прогресс показывает опыт аккаунта; покупка постоянных боевых преимуществ и отдельная экономика пока не добавляются.

## Интернет и разрывы соединения

Первую внешнюю проверку проводим уже на коротком бою. Сервер размещается отдельно от компьютеров игроков; друзья подключаются к его HTTPS/WSS адресу. Упаковку, адрес и настройки сервера проверяем на другом компьютере, а не только в двух окнах на одном.

Предлагаемое окно переподключения — 30 секунд. На разрыве ввод сбрасывается, персонаж остаётся в мире и может получить урон; бой для остальных продолжается. Повторный вход того же аккаунта возвращает существующего персонажа и его состояние. После таймаута применяется правило выбывания, определённое на этапе боя. Новый вход не создаёт второго персонажа и не сбрасывает здоровье или улучшения.

Проверяем задержку, обрывы, закрытие клиента, повторное подключение и остановку сервера. Переход на UDP, бинарный протокол или дополнительный сетевой сервис рассматривается только при измеренной необходимости.

## Графика и звук

Основа уже выбрана: 0x72 DungeonTileset II, пиксельная графика и тёмная фэнтезийная палитра. Автор указывает CC0 на странице набора. Сохраним источник и файл условий вместе с ресурсами проекта; условия сторонних дополнений проверяются отдельно.

Для первого уровня нужны пол, стены, несколько препятствий, маг и противник. Разных игроков различаем цветом, контуром и именем. Снаряды, рывок, попадания и предупреждения атак босса можно рисовать простыми эффектами libGDX, сохраняя общую палитру. Недостающего босса можно собрать из изменённого спрайта и собственных кадров, сохранив условия исходника.

Пиксельные текстуры используют ближайшую фильтрацию; правила камеры, масштаба и общих размеров спрайтов определяются при подключении первого набора. Сначала важны читаемость персонажей, опасностей и здоровья, затем декоративные эффекты. В игровой сцене не используются эмодзи как замена спрайтам.

Звук добавляется к уже готовым действиям: выстрел, попадание, рывок, уровень, урон и босс. У каждого внешнего звука должен быть понятный источник и условия использования; для релизного комплекта составляется список авторов.

Сейчас ничего скачивать не требуется. При подключении набора графики или WebSocket-зависимостей пользователь получит отдельные инструкции и сам выполнит загрузку, как было согласовано.

## Граница первой законченной версии

Один герой, одна арена, три обычных врага, один босс, 6–8 улучшений, комнаты для 2–4 игроков, сохранение результатов и один размещённый сервер. Разработчик может тестировать мир по отдельности; обычный совместный матч сохраняет минимум двух участников.

Несколько классов и арен, инвентарь, крафт, торговля, открытый мир, рейтинговый подбор и микросервисы остаются за пределами первого выпуска.

Для портфолио результат сопровождается кратким видео совместного забега, схемой архитектуры, скриншотами, инструкцией запуска и тестами важных игровых правил. Нагрузочная проверка воспроизводит согласованную максимальную сцену с четырьмя игроками; по ней фиксируются реальные ограничения, а не произвольные обещания числа комнат.

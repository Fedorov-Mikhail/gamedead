# «Печать сумрака»: архитектура и первый этап

Статус: архитектура принята пользователем 2026-10-15; подготовка плана реализации первого этапа.

## Цель и принятые требования

Одиночный разработчик с небольшим опытом создаёт игру для себя, друзей и портфолио. Настольный клиент написан на Java и libGDX, сервер — на Spring Boot, данные — в PostgreSQL. Сборка всего проекта — Gradle, по последнему пожеланию пользователя.

Игра — кооперативное фэнтезийное выживание на фиксированной арене для 2–4 игроков. Плановая продолжительность успешного забега — около 30 минут; поражение может завершить его раньше. WASD — движение, мышь — прицеливание, левая кнопка — атака, Shift — рывок. Опыт команды общий, выбор улучшений личный. Уровень забега сбрасывается, постоянный опыт аккаунта сохраняется отдельно.

Начальная игровая версия: одна арена, один маг, три обычных врага, один босс, 6–8 улучшений. Графическая основа — пиксельный набор 0x72 DungeonTileset II, дополнительные эффекты и интерфейс создаются в согласованном стиле. Графика и игровой контент не входят в первый серверный этап.

## Границы первого этапа

Результат: собираемый сервер, воспроизводимые миграции и API регистрации, входа, просмотра собственного профиля и выхода. Комнаты, WebSocket, игровой цикл и графический клиент добавляются следующими отдельными этапами. Базу и схему пользователь уже создал, повторно создавать или очищать их нельзя.

Первым реализуется сервер с модулем общих сообщений. Два остальных модуля добавляются при начале соответствующего этапа, чтобы не создавать пустые компоненты.

## Модули и зависимости

Один репозиторий и многомодульный Gradle-проект. Базовый Java package — `com.gamedead`. Скрипты сборки используют Groovy DSL: корневые `settings.gradle` и `build.gradle`, отдельный `build.gradle` в каждом модуле. Состав модулей объявляется в `settings.gradle`; первым этапом подключаются только `protocol` и `server`.

| Модуль | Назначение | Зависимости внутри проекта |
|---|---|---|
| `protocol` | Java records запросов, ответов, ошибок; позднее игровых сообщений | Нет |
| `server` | Spring Boot, аккаунты, сессии, БД; позднее комнаты и выполнение игры | `protocol`, позднее `game-core` |
| `game-core` | Правила и расчёт игрового мира без Spring, графики и доступа к БД | Нет |
| `client` | libGDX, настольный запуск, экраны, ввод, звук и сеть | `protocol`, позднее модуль движения из `game-core` |

Клиент не зависит от серверных сущностей и репозиториев. Protocol не содержит JPA и Spring. В игровом ядре нет OpenGL и libGDX: сервер должен запускаться без графического окружения. Идентификаторы в API — UUID и строки с явными значениями, а не JPA-объекты.

Внутри сервера пакеты организуются по назначению: `auth`, `account`, `config`, `error`; позднее `room` и `match`. Контроллеры отвечают за HTTP, сервисы — за операции и транзакции, репозитории — за хранение.

## Инструменты

- Java 21; установлен Oracle JDK 21.0.12.1.
- Gradle 9.8.1 через Gradle Wrapper; версия и SHA-256 дистрибутива закрепляются в `gradle/wrapper/gradle-wrapper.properties`. Скрипты `gradlew` и `gradlew.bat` и файлы Wrapper входят в репозиторий. Java toolchain и целевая версия компиляции — 21.
- Spring Boot 4.1.1; версии Spring Security, Hibernate и Flyway управляются BOM Spring Boot.
- Spring MVC, Spring Security, Bean Validation, Spring Data JPA, PostgreSQL JDBC, Flyway с модулем PostgreSQL.
- Версия libGDX фиксируется перед клиентским этапом; настольный backend — LWJGL3. Зависимости libGDX и платформенные native-библиотеки подключаются только к клиенту. Структура desktop-клиента сверяется с актуальным Gradle-проектом генератора gdx-liftoff и проверяется отдельным запуском.
- JUnit Jupiter 6.0.3 из BOM Spring Boot 4.1.1; интеграционные проверки — на PostgreSQL в отдельной тестовой БД. H2 не подменяет PostgreSQL. Версия уточнена при реализации: выбранный Spring Boot управляет JUnit 6, поэтому отдельный устаревший BOM JUnit 5 не используется.

Gradle Wrapper загружает Gradle, Gradle загружает зависимости. Ручная установка Spring, libGDX или отдельного Gradle не требуется. Интернет нужен для первой сборки. IntelliJ IDEA уже обнаружена на компьютере. Docker не является обязательным инструментом первого этапа.

Плагин Spring Boot применяется только к `server`; библиотечные модули используют `java-library`, будущий desktop-клиент — `application`. Общие версии задаются централизованно, динамические версии запрещены. BOM Spring Boot подключается средствами Gradle в сервере и не навязывает зависимости клиенту или игровому ядру.

Команды будущего проекта для Windows PowerShell:

- `./gradlew.bat build` — сборка и модульные тесты подключённых модулей, без подключения к пользовательской БД.
- `./gradlew.bat :server:bootRun` — запуск сервера; параметры БД вводятся локально через переменные окружения.
- `./gradlew.bat :server:integrationTest` — отдельная задача PostgreSQL-проверок; создаётся при реализации тестового профиля и требует настроенной `gamedead_test`.

Эти команды описывают планируемый интерфейс сборки. Wrapper, скрипты и задачи пока не созданы.

## Существующая база и миграции

База `gamedead`, пользователь приложения `gamedead_app`, схема `game`, кодировка UTF8. Временные отметки — `timestamptz`, Java `Instant`, рабочий часовой пояс UTC. UUID генерирует приложение; расширение pgcrypto не требуется.

Пароль БД пользователь вводит локально. Сервер читает `GAMEDEAD_DB_URL`, `GAMEDEAD_DB_USERNAME`, `GAMEDEAD_DB_PASSWORD`. Адрес по умолчанию — `jdbc:postgresql://localhost:5432/gamedead`, пользователь — `gamedead_app`; для пароля нет встроенного значения. Пароль не включается в репозиторий, документацию, клиент или вывод диагностических команд. Наличие переменных проверяется без печати значений.

Миграции лежат в `server/src/main/resources/db/migration`. Flyway использует схему `game`, включая свою таблицу истории; схема должна существовать. Hibernate работает с `ddl-auto=validate`, его default schema — `game`. Автоматический baseline и Flyway clean отключены. Применённые миграции не редактируются, новые изменения получают следующий номер.

### Первая миграция: `V1__create_accounts_and_sessions.sql`

| Таблица | Поля и ограничения |
|---|---|
| `accounts` | `id uuid PK`, `login varchar(24) NOT NULL UNIQUE`, `password_hash varchar(255) NOT NULL`, `enabled boolean NOT NULL DEFAULT true`, `created_at timestamptz NOT NULL`, `last_login_at timestamptz NULL` |
| `player_profiles` | `account_id uuid PK FK accounts(id) ON DELETE CASCADE`, `display_name varchar(24) NOT NULL`, `account_xp bigint NOT NULL DEFAULT 0 CHECK >= 0`, `appearance_id varchar(64) NOT NULL DEFAULT 'mage_default'`, `updated_at timestamptz NOT NULL` |
| `auth_sessions` | `id uuid PK`, `account_id uuid NOT NULL FK accounts(id) ON DELETE CASCADE`, `token_hash varchar(64) NOT NULL UNIQUE`, `created_at timestamptz NOT NULL`, `expires_at timestamptz NOT NULL`, `revoked_at timestamptz NULL` |

`login` хранится в нижнем регистре, CHECK разрешает только `[a-z0-9_]{3,24}`. Дополнительные CHECK: `display_name` после trim имеет 3–24 символа, `expires_at > created_at`, `revoked_at` при наличии не раньше `created_at`. Индексы: `auth_sessions(account_id)` и `auth_sessions(expires_at)`; PK и UNIQUE уже создают свои индексы.

Регистрация аккаунта и профиля выполняется одной транзакцией. `last_login_at` обновляется в транзакции создания сеанса. `account_xp` меняется только сервером, API изменения опыта на первом этапе отсутствует.

Таблицы `matches`, `match_players` и открытых наград создаются при реализации матчей. Их ответственность уже определена: результаты, статистика, итоговая сборка и однократное начисление наград. Координаты, враги и снаряды в БД не записываются на каждом игровом шаге.

## Регистрация и вход

Регистрация принимает логин, отображаемое имя и пароль. Логин обрезается по краям и переводится в нижний регистр через `Locale.ROOT`; отображаемое имя обрезается по краям. Имя допускает кириллицу, но не управляющие символы. Ограничение длины имени проверяется в Unicode code points. Отображаемые имена не обязаны быть уникальными.

Пароль не обрезается и не нормализуется: минимум 8 Unicode code points, максимум 72 байта UTF-8. Это исключает неоднозначность и усечение BCrypt. Хранение — Spring Security DelegatingPasswordEncoder, BCrypt с cost 12 и идентификатором алгоритма. Стоимость измеряется на целевой машине перед внешним развёртыванием.

Вход принимает логин и пароль, возвращает случайный токен из 32 криптографически случайных байт в Base64URL без padding и срок действия. В БД записывается только SHA-256 хеш токена; для высокоэнтропийного токена такой хеш подходит, BCrypt остаётся для паролей. Срок сессии — 8 часов, без автоматического продления. Возможны несколько независимых сессий аккаунта. Клиент передаёт `Authorization: Bearer <token>` и в первой версии хранит токен только в памяти.

Просроченный, отозванный, неизвестный токен и сессия выключенного аккаунта дают 401. Выход отзывает текущую сессию. После перезапуска сервера неистёкшая сессия продолжает работать, так как хранится в PostgreSQL. Refresh tokens, email и восстановление пароля в этот этап не входят.

### HTTP-контракт

| Запрос | Успех | Ошибки |
|---|---|---|
| `POST /api/v1/auth/register` — `login`, `displayName`, `password` | 201: `accountId`, `login`, `displayName`; затем требуется вход | 400 неверные данные, 409 логин занят |
| `POST /api/v1/auth/login` — `login`, `password` | 200: `accessToken`, `tokenType=Bearer`, `expiresAt` | 400 неверный формат, 401 неверные учётные данные, 429 лимит попыток |
| `GET /api/v1/me` — Bearer | 200: `accountId`, `login`, `displayName`, `accountXp`, `appearanceId` | 401 |
| `POST /api/v1/auth/logout` — Bearer | 204 | 401 |

JSON-ошибки имеют поля `code`, `message`, `fieldErrors` (объект поле → сообщение). Поля хешей, паролей и сырых токенов никогда не попадают в ответы профиля, ошибки и логи. Неверный пароль, неизвестный логин и выключенный аккаунт используют одинаковую ошибку входа; для неизвестного логина выполняется BCrypt-проверка фиктивного хеша.

Cookie-аутентификация, Basic и стандартная HTML-форма отключены; приложение использует только Bearer. Для такого API CSRF отключён, CORS по умолчанию не открыт. Максимальное тело auth-запроса — 8 KiB, превышение возвращает 413. Повреждённый JSON возвращает 400. До внешнего доступа требуются HTTPS и ограничитель: не более 10 запросов входа и 5 регистраций за минуту с IP, 429 с Retry-After. На первом односерверном этапе счётчики в памяти, срок их хранения ограничен; локально применяются те же правила. При reverse proxy доверять forwarded IP можно только от настроенного доверенного прокси.

## Дальнейшая игровая архитектура

Один процесс Spring Boot обслуживает HTTP и WebSocket. Каждая комната имеет изолированное состояние, команды игроков обрабатываются последовательно игровым циклом. Сетевые потоки кладут команды в ограниченные очереди и не изменяют мир непосредственно. WebSocket аутентифицируется сессией, введённый клиентом accountId не используется как источник личности.

Стартовые параметры для проверки: расчёт 20 раз/с, снимки 10–20 раз/с, отрисовка около 60 кадров/с; клиент сглаживает состояния. Приоритет раннего сетевого прототипа — движение, задержка, переподключение и ограничение нагрузки. Переход на другой транспорт определяется измерениями.

Тридцатиминутный забег включает волны, короткие передышки и бой с боссом. Баланс и точное расписание — следующий игровой документ, без жёсткой привязки к прежним пяти волнам. Отдельный фиксированный таймер ограничивает матч; паузы выбора учитываются в общей плановой длительности. Финальные результаты записываются одной транзакцией, уникальность участия в матче предотвращает повторное начисление.

## Проверки первого этапа

- Сборка через Gradle Wrapper под JDK 21; сервер не тянет графические native-библиотеки. Обычный `build` не требует подключения к PostgreSQL, интеграционные проверки запускаются отдельной задачей `:server:integrationTest`.
- Миграция на пустой отдельной тестовой БД и повторный запуск без изменения данных; в пользовательской базе тесты не запускаются.
- Регистрация создаёт аккаунт и профиль атомарно; параллельная регистрация одинакового нормализованного логина даёт один успех и один 409.
- Проверки границ логина, Unicode-имени, пароля, в том числе UTF-8 >72 байт без усечения.
- Вход, профиль, сохранность сессии при перезапуске, выход, истечение и блокировка аккаунта; время берётся через внедряемый Clock.
- Неверный токен, повреждённый JSON, слишком большое тело и лимиты запросов дают согласованные ответы без секретов.
- При недоступной БД или неверных параметрах сервер сообщает об ошибке запуска, не создаёт обходную временную базу.

Тестовую БД `gamedead_test` подготавливают отдельно. По умолчанию интеграционные проверки не подключаются к `gamedead`; тестовый профиль дополнительно проверяет имя БД. Отсутствие тестовой БД не скрывается как успешное выполнение интеграционных проверок. Локальный пароль вводит пользователь при запуске, в чат его передавать не требуется.

## Критерий готовности

Сервер воспроизводимо собирается, применяет V1 без удаления существующих объектов, позволяет зарегистрировать два аккаунта, войти каждым, получить собственный профиль и завершить сессию. После перезапуска сохранены аккаунты, профили и действующие сессии. Инструкция запуска содержит локальную настройку пароля и адреса БД. Игровое окно не является результатом этого этапа.
